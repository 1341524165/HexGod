# 出装顺序与数据接口核查（2026-09-27）

## 能否直接接到 WeGame 同等的完整路径 API？

此次没有核实到可直接接入、覆盖国服海克斯大乱斗的官方完整路径 API。WeGame 有推荐出装功能，但“产品中能展示”不能证明有开放给第三方的开发接口。

| 来源 | 已核实内容 | 尚不能承诺的内容 |
| --- | --- | --- |
| [WeGame 官方功能页](https://www.wegame.com.cn/helper/lol/setting/setting.html) | 有装备推荐功能介绍 | 没有找到公开开发文档、接入授权与按购买位置的字段定义。不能称为已可接入的开放 API |
| [Riot 官方接口目录](https://developer.riotgames.com/apis#match-v5) / [LoL 文档](https://developer.riotgames.com/docs/lol) | 有原始对局类接口；本机 Live Client Data 能提供当前物品状态 | 本机装备接口没有全服推荐路线与胜率；不能据此承诺国服海克斯模式的全量历史与顺序聚合 |
| [ARAMGG 开放数据说明](https://aramgg.com/zh-CN/client) / [开发者入口](https://data.dtodo.cn/developer.html) | 官方站点说明第三方可申请免费 API Key，查询接口说明和额度 | 此次开发者页和公开文档抓取超时，未核实按第几件、已有装备前缀、海克斯组合的完整路径字段，也未实测访问额度或取得 Key |
| [ARAMGG 客户端接口分发说明](https://github.com/valkia/aramgg_client/blob/master/docs/client-api-strategy.md) | 第三方接口采用 Key、credits 与限流；有版本化数据分发 | 第三方数据服务不等同于腾讯 / Riot 官方统计。客户端公开地址不能替代第三方授权与字段核对 |

项目目前没有接入上述第三方远程推荐服务，仍使用随包 16.15 数据。没有注册账号、申请 Key 或上传用户对局信息。

## 为什么原来会推荐人马先出公理圆弧？

已用本地后端复现：旧精选核心表包含公理圆弧，排序又额外加了 6 分。本地单件统计中，公理圆弧约 58.99% / 7,405 场，青龙刀约 51.23% / 160,544 场。这里的样本是持有该装备的记录，既没有第一件购买位置，也没有相同前置装备的条件。因此不能用 58.99% 得出“首件公理最好”。

另一个数据问题是魔宗和魔切分别统计：魔宗约 43.09% / 4,505 场，魔切约 52.53% / 140,192 场。不能直接合并两者或把魔切的胜率改名显示成魔宗的首件胜率。

0.9 的修正：

- 用独立 `item_order.json` 记录明确的顺序参考。人马按本次需求使用 **朔极之矛 → 魔宗（叠满转魔切）**；完成两件前，公理圆弧不进入主候选。持有魔切也视为已完成魔宗路线。
- 该路线标为人工顺序参考，路径样本数为空；单件百分比仍保留原装备 ID 的统计。海克斯机制建议继续单列，不能抢占路线第一项。
- 其他英雄没有伪造一套“权威顺序”。库存已同步且尚无成装时，在至少 250 场、使用量达到该英雄最常用候选 40% 的装备中比较，减少罕见收尾装靠总体高胜率排在首件的情况。若没有满足条件的候选，则保留原候选。阈值是工程上的保守筛选，不是首件统计证明。
- 狂徒被动门槛、可购买地图、进化形态映射和已有装备排除继续生效。出门装仍是独立方案。

## 真正完整的路径数据必须验证什么？

至少需要：游戏模式和区服、补丁与日期、英雄、此前成装的购买顺序、下一件装备、胜场数 / 总场数。若要证明海克斯联动，还需要当时已选海克斯；否则只可作为无海克斯条件的路线参考。

“六件装备列表”“核心三件套”“拥有某物品的胜率”和“按顺序购买这套装备的胜率”是不同的统计。接入任何 API 前，需要拿同一英雄的实际响应验证这些区别，以及售卖、撤销购买、自动进化、鞋子计数的处理方式。

## 切换修复与验证

- OCR 默认尝试间隔从 1 秒改为 0.5 秒，不并发堆积识别。游戏接口另一个本地后端每 1 秒轮询，接口等待不堵住 OCR 请求队列。
- 开局未记录首个海克斯，以及三选一可见时主动检查标题；普通阶段也每 2 秒绕过视觉预筛重新检查，仍保留非三选一文字排除。
- 出现面板但暂未读出标题，显示海克斯识别状态；已读结果允许短暂漏字，超过 1.2 秒不再显示旧标题。连续两次确认面板消失（间隔至少 0.4 秒）才退回装备。
- 正常选择后立即切换；已开始处理的旧截图和相同选项的退场动画不会把界面切回去。识别到新的选项时重新显示。跳过截图不算作面板消失，超过 2.5 秒没有有效画面时清理显示。
- 真实游戏截图尝试不同布局时，保留原游戏窗口与捕获时间；这避免替代布局识别成功却失去点击记录上下文。
- 悬浮窗请求 Windows 从截图中排除自身，减少自身文字遮挡 OCR；是否生效仍取决于系统与捕获方式。
- `overlay-events.log` 在模式切换时保存时间、英雄、阶段、已选、主装备候选 ID 和识别原因；不保存截图、账号或聊天。超过 1 MiB 后重新开始记录。这是阶段诊断，不是完整逐局战绩统计。

69 项 Python 测试及 WPF 场景测试通过。测试覆盖真实 OCR 模型的合成开局截图、替代布局的点击坐标、首件筛选、人马购买进度、面板读字中 / 短暂漏帧 / 点击旧帧 / 下一轮选项 / 新进程 / 装备刷新。国服真实对局尚未验证，不能把合成测试视为游戏中的识别成功率。
